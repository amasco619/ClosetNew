# R-13 — Check my look judge input inventory

**Scope:** Read-only inventory of the Check my look request, garment inputs, profile constraints and final judge text. No product code was changed, no migrations or database queries were run, and no Gemini generation call was made. The only file added is this requested report.

## How the data reaches the judge

The client sends only `selection`, `brief`, and optional `garmentFacts`; the client helper reconstructs this envelope rather than forwarding profile, tier or other caller data (`lib/checkLookClient.ts:78–92`). The request schema is strict (`server/checkLookJudgeInput.ts:81–106`). The authenticated server then loads the user's selected wardrobe rows, confirmed groups and `user_profiles.constraints` (`server/checkLookJudgeRoute.ts:43–80`), validates selection and assigned-set membership, and builds the guard and export text (`:140–158`).

The garment rows are fetched by authenticated owner and mapped from the app's saved item schema (`server/checkLookJudgeRoute.ts:51–79`; `lib/wardrobeMapper.ts:21–40`). The provider receives the fixed system prompt plus the allowlisted export text, not the client JSON itself (`server/checkLookJudge.ts:90–102`). When the feature flag is disabled, the route returns its local-check directive before request parsing or export (`server/checkLookJudgeRoute.ts:107–115`).

## 5. What `exportJudgeText` actually sends

`exportJudgeText` builds the prompt from `Brief`, profile constraints, deterministic guard facts and selected `Items` (`server/checkLookJudgeInput.ts:259–310`).

| Export block / label | Inputs and treatment |
|---|---|
| `Brief` | `context`, `venue`, `dress_code`, `denomination`, `role`, `announced_colours`, `time_of_day`, `assigned_set`, `temperature_c`. Missing optional values become `null`; assigned set is member descriptions rather than a raw UUID. |
| `Coverage and never-wear constraints` | Parsed server-side profile constraint keys that are present, plus normalised `minimumSleeveLength` and compatibility `noSleeveless`. |
| `Deterministic guard facts` | Machine-generated `{pass, failures, missing, flags}`; not a user-entered field. |
| `Items` | One line per selected item, sorted. `Name` is safe subtype or category fallback; `Colour` is canonical or `unknown`; `Fabric` is included only when allowlisted; `Quality` is always literal `unknown`; `Notes` may include pattern, sleeves, fit, neckline, integer formality, weight and per-look facts. |

### Specifically requested answers

**a. Formality.** It is not returned by Gemini. A user can optionally type a 1–10 personal rating in the expanded single Add Item details; bulk edit has no formality control. The field is visible but requires the user to supply the score. The exporter sends only an integer 1–10 as `formality N` in Notes; an entered decimal is accepted and stored by the UI but is not exported.

**b. Fit, neckline, pattern, sleeve length, subtype, colour and fabric.** Their exact options and suppliers are in the garment table above. In brief: fit has five classifier/user values; neckline nine; pattern nine; sleeves four; subtype is category-specific; colour uses the 26 UI colour families; fabric has 17 UI values. All are classifier-prefilled where the classifier schema supports them and user-editable, except classifier output for outerwear neckline/sleeve is not requested by its prompt (the user can still edit those fields).

**c. Fields that require guessing.** Formality is a personal 1–10 score with only endpoint anchors (relaxed/formal). Weight is also a visual estimate (`light`/`mid`/`heavy`); the Add Item helper explicitly says to leave it unset if unclear. Fabric has a “pick the closest match” prompt. The export does not treat weight as quality.

**d. Exported fields not directly shown as user fields.** `Quality: unknown` is a fixed exporter string; there is no stored quality field or quality control. The `{pass, failures, missing, flags}` guard object is generated internally and sent as structured text, rather than shown to the user in that form. Profile constraints themselves have controls in Profile. Raw user description, photo, item IDs, price, pattern scale, accent colour, metal tone, seasons, rise, warmth, and dominant colour coordinates are not sent.

**e. Single versus bulk.** Both flows let the user edit category, subtype, primary colour, occasion tags, season tags, fit, pattern, pattern scale, fabric, weight, neckline, sleeve length and description. Single Add Item additionally offers formality, rise, warmth, accent colour, metal tone and purchase price. Bulk has no controls for those fields; some classifier-prefilled `rise`, `warmthBand` and `accentColor` values are retained, but not editable there. Single Add Item has manual-only jewelry subtype options `gyale`, `kallabi`, `mayafi`, `hijab`; bulk does not. Fabric/pattern controls also differ by category: single shows textile details for selected textile jewelry and pattern for shoes/bags, while bulk limits those fields to core garments. The subtype export fallback noted above applies to both.

## Findings to carry forward

1. The request does not carry item metadata or profile constraints from the client: it carries selected UUIDs, brief and per-look facts. The server reloads owner-scoped data and builds a restricted text representation.
2. `selection.occasion` is accepted but not separately included in judge text; the judge sees `brief.context` instead.
3. Current `colorAversions` UI includes `neon`, but the profile parser's colour enum does not. That saved preference can make the profile lookup return 503.
4. Current sheet can select more than eight funeral colours even though the request schema caps the list at eight.
5. Not Sure is intentionally represented differently by fact: sleeve length and sleeve lining can export unknown; hem and back/strap Not Sure are omitted because their request schema has no unknown value.
6. The current text instruction for Ask in `server/checkLookJudgeInput.ts:295–298` lists five missing-fact names and omits `sleeve_length`, although route/client enums include that fact. This is a prompt/schema inventory discrepancy.
7. No value from this inventory was sent to Gemini during this review. No changes beyond this report file.
