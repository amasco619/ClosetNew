# Amodka Payments & Entitlements Readiness Audit

**Scope:** Read-only repository audit, 27 September 2026. No live store, production database, Supabase dashboard, or device purchase was inspected. “Missing” below means not found after searching application, server, migrations, configuration, dependencies, tests, and payment documentation; it does not assert the state of external dashboards. The existing payment requirements document is **not** an implementation record (`docs/compliance/phase5c-payment-architecture.md:1-16`).

## 1. Executive Summary

**Overall status: NOT IMPLEMENTED** for paid subscriptions. The app has a Premium information screen, local feature gates, a server entitlement read, an expiry-aware resolver, and a server-checked PhotoRoom quota, but no purchasable product, billing SDK, purchase or restore action, store verification, transaction ledger, or store notification handler (`app/premium.tsx:82-115`; `package.json:23-81`; `server/routes.ts:228-234,396-406`; `server/entitlements.ts:15-60`). Paid Premium must not launch in this state.

**Conditional P0 trust-boundary concern:** The checked-in `user_profiles` RLS policies restrict *which row* a signed-in user can insert/update, not *which columns*. The client already writes that table directly. No checked-in column privilege, trigger, or constraint prevents an authenticated user from writing `premium=true` and a future `premium_expires_at`; the server then trusts those fields (`supabase/migrations/20260610000000_user_profiles_rls.sql:18-43`; `lib/database.ts:12-34`; `server/entitlements.ts:15-42`). Whether the deployed DB has separately restricted `authenticated` table/column privileges is **not verified**. Treat paid launch as blocked until read-only grant/policy inspection resolves this, then protect premium columns at the database boundary if exposed. Omitting `premium` from the normal TypeScript helper is not a security control.

Current app-session access can also remain stale: a failed token-refresh entitlement request retains the prior in-memory Premium value, and no client-side expiry timer was found (`contexts/AppContext.tsx:347-361,875-886`). The PhotoRoom server independently checks the DB expiry, but most other gates are client-only. No tests or store purchases were executed for this audit.

## 2. Current Architecture

The client calls authenticated `GET /api/user/entitlements`; the server obtains the user from the bearer token and reads `user_profiles.premium` and `premium_expires_at` using its admin client. Premium is true only when the flag is true and expiry is a valid future date (`lib/entitlements.ts:6-18`; `server/routes.ts:197-225,396-406`; `server/entitlements.ts:15-42`). `applyVerifiedEntitlement` can write those fields on the server but is only a future-payment boundary, not a registered purchase/webhook route (`server/entitlements.ts:44-60`). No verified store event currently drives it.

`AppContext` starts non-Premium, loads the server result on hydration, and refreshes it on a token refresh; it clears Premium on `SIGNED_OUT` (`contexts/AppContext.tsx:225-231,282-361,875-886`). Most wardrobe/styling distinctions use this in-memory boolean. PhotoRoom separately reads the server entitlement and applies a persistent per-user quota (`server/remove-background.ts:87-169`; `server/bgRemovalStore.ts:128-165,202-209`). There is no client purchase-to-server-confirmation sequence (`app/premium.tsx:82-115`; `package.json:23-81`).

## 4. Entitlement Lifecycle

**User → paywall/product selection:** Profile/feature upsells lead to a Premium information screen, but there are no selectable or purchasable plans (`app/(tabs)/profile.tsx:682-720`; `app/premium.tsx:82-115`). Identifiers for two intended periods are hard-coded **in documentation only**, not environment-driven runtime product IDs (`docs/compliance/phase5c-payment-architecture.md:43-49,77-89`).

**Store purchase → verification → entitlement record:** Not implemented for either store. Neither client purchase/restore calls nor server receipt/token validation nor payment-bound writes were found (`package.json:23-81`; `server/routes.ts:228-234,396-406`; `server/entitlements.ts:44-60`). StoreKit 2 and Play Billing are requirements, not in-use APIs (`docs/compliance/phase5c-payment-architecture.md:43-99`). A forged/replayed receipt cannot be submitted to a current payment endpoint because none exists; this is **not** evidence future verification/replay protection is safe.

**Entitlement → client session → feature access:** Existing server read and client hydration are real (`server/routes.ts:396-406`; `contexts/AppContext.tsx:875-886`), but their DB fields have no demonstrated store provenance and are potentially directly client-writable (Executive Summary). Cold offline start defaults free; a transient refresh failure after Premium was loaded keeps the previous UI state (`contexts/AppContext.tsx:225,347-361`). Server resolver checks expiry on each request; client has no expiry countdown or periodic entitlement recheck (`server/entitlements.ts:15-24`; `contexts/AppContext.tsx:347-361,875-886`).

**Renewal / cancellation / expiry / billing retry / grace / refund / revocation:** No store event ingestion. If someone externally updates the DB and a refresh succeeds, the changed expiry/flag can reach the client; expiry alone affects server reads immediately, not necessarily an already-open UI. Cancellation-at-period-end, grace, account hold, renewals, refund, and revocation are not modeled by a subscription record or event processor (`server/entitlements.ts:3-60`; `docs/compliance/phase5c-payment-architecture.md:60-69,90-99,148-196`).

**Restore / accounts / deletion:** There is no store restore, transaction-to-account ownership mapping, or account-linking policy; another device using the *same* Amodka account can fetch its existing DB flag, which is not proof of a restored store purchase (`lib/entitlements.ts:14-18`; `server/routes.ts:396-406`). Sign-out clears client Premium and account data; `SIGNED_IN` hydration uses user/generation guards (`contexts/AppContext.tsx:285-345`). Account deletion removes the profile row and Auth account but does not manage store subscriptions or future payment records (`server/routes.ts:68-125`).

## 6. Security & Trust Boundary

**CLIENT CLAIM:** Local `isPremium`, a modified client, AsyncStorage, a request body, or a JWT's old premium claim must not grant paid rights. Client upsert's omitted TypeScript property and UI gating alone do not prevent direct authenticated Supabase REST access (`lib/database.ts:12-34`; `supabase/migrations/20260610000000_user_profiles_rls.sql:18-43`). The current client does not read local Premium storage (`__tests__/entitlements.test.ts:130-135`).

**STORE-VERIFIED FACT:** None is processed in the repository. No purchase/token/transaction signature validator or verified event store was found (`package.json:23-81`; `server/routes.ts:228-540`; `docs/compliance/phase5c-payment-architecture.md:43-99,183-196`).

**SERVER-AUTHORITATIVE ENTITLEMENT:** The server uses the authenticated user ID and current DB fields, not caller-supplied user IDs or a JWT premium flag (`server/routes.ts:197-225,396-406`; `server/entitlements.ts:15-42`; `server/remove-background.ts:126-139`). This is authoritative only if premium DB columns cannot be client-mutated. The checked-in row policies permit own-row INSERT/UPDATE without column restriction; live grants/triggers remain unverified (`supabase/migrations/20260610000000_user_profiles_rls.sql:18-43`). An attacker able to set those fields could obtain the Premium PhotoRoom quota and Premium responses without a purchase. Other local gates can be bypassed by modified clients even when the DB is secure. The retired HTTP grant route is 404 in tests, but route removal does **not** resolve direct DB writes (`__tests__/entitlements.test.ts:101-110`).

An old successful purchase response has no current endpoint to replay; future purchase/restore integration must bind original transaction/purchase token to a single account, re-query trusted store/provider status, validate environment/product, and deduplicate transitions. Cross-account entitlement theft cannot be ruled out for future implementation without that binding. Existing sign-out clears the local state, while refresh failure and no client expiry timer leave stale in-session UI gates (`contexts/AppContext.tsx:327-361`). Do not rely on the Premium UI as the financial boundary.

No Apple ASSN v2, Google RTDN/Pub/Sub or intermediary billing-provider webhook route, verifier, event journal, replay/duplicate protection, account association, lifecycle transition, unknown-event policy, or delivery retry handler was found (`server/routes.ts:228-540`; `server/entitlements.ts:44-60`; `docs/compliance/phase5c-payment-architecture.md:183-196`). ## 11. Account Deletion Interaction

Authenticated deletion checks the supplied user ID equals the validated account; the public deletion path first verifies an email OTP. Both call `deleteAccountData`, which removes flat user storage objects, listed user-owned tables, `user_profiles`, then the Auth user (`server/routes.ts:68-125,408-425,489-533`). This removes the present DB entitlement row when the process completes. The function has an explicit table list and no payment ledger/token cleanup because none currently exists. It is non-transactional: a later failure can leave partially deleted data; retries are possible but no durable reconciliation is implemented (`server/routes.ts:68-125,419-425`).

Apple/Google subscription status outside Amodka is not cancelled by deleting an account. Future store notifications could arrive after deletion, and a future payment-token/account link could accidentally re-provision access unless deletion, orphan events, and restore/account relinking are specified. No current notification handler exists to create that race today. Whether transaction evidence must be retained for legal/store obligations requires a separate legal/retention decision; do not infer permission to retain or delete it from this repository (`server/routes.ts:68-125`; `docs/compliance/privacy-policy-source.md:135,237-239`).

## 12. Privacy / Data Handling

Present payment-related state is limited to the `premium` flag, expiry timestamp, account identifier and per-user background-removal usage count; the client receives `isPremium`/`expiresAt` via authenticated GET (`server/entitlements.ts:3-42`; `server/bgRemovalStore.ts:60-65`; `lib/entitlements.ts:1-18`). Purchase price/CPW in wardrobe items is garment metadata, **not** a billing transaction (`constants/types.ts:96`; `app/item-detail.tsx:239-307`). No payment card details, store transaction IDs, original transaction IDs, purchase tokens, receipts, billing currency/country or provider account IDs are handled by present payment code (`app/premium.tsx:82-115`; `server/routes.ts:228-540`).

There are therefore no present receipt/token logs to evaluate. Future handlers should store only necessary IDs, status and timestamps, redact tokens/JWS and webhook payloads from logs, limit server access, and define deletion/retention and account-linking rules before collecting them. Existing compliance text itself says payment metadata is not yet implemented (`docs/compliance/privacy-policy-source.md:135,237-239`). This is a technical inventory, not a legal conclusion.

## 17. Minimum Safe Implementation Scope

**Not authorized by this report.** For a later implementation approval, the smallest paid-subscription slice is:

1. Verify live `user_profiles` privileges/policies/triggers read-only, then ensure authenticated clients can still edit ordinary profile fields but **cannot** INSERT/UPDATE Premium fields; test a direct malicious Supabase request in a safe test environment. Preserve existing Auth and item persistence architecture (`supabase/migrations/20260610000000_user_profiles_rls.sql:18-43`; `lib/database.ts:12-34`).
2. Decide on **one** supported cross-platform billing route and a minimal monthly/annual product catalog. Add only the required native billing integration and purchase/restore/status UI. The documentary IDs are proposals, not working products (`docs/compliance/phase5c-payment-architecture.md:43-49,77-89`; `app/premium.tsx:82-115`).
3. Bind a verified store transaction/token to the authenticated account on the server. Make an idempotent entitlement update only from verified provider facts; track minimal transaction ownership and last effective expiry/status. Validate duplicates, cancellation-at-period-end, renewal, grace, refund, revoke, account switch, and deletion races. Use current expiry-aware resolver after protecting its backing DB fields (`server/entitlements.ts:15-60`).
4. Make PhotoRoom's existing paid-provider quota reservation atomic. Only if an approved product policy actually sells additional metered AI or storage capacity, enforce those specific limits at a trusted API/storage boundary; do not invent a classification allowance or relocate the local outfit engine just for billing. Keep local rotation/upsell code for UX. Do **not** change the recommendation algorithm or classifier taxonomy (`server/bgRemovalStore.ts:128-165`; `constants/outfitRotation.ts:645-655`; `lib/database.ts:51-82`).
5. Mock unit/integration tests for verification, invalid/foreign/replayed tokens, entitlement transitions, direct profile-write rejection, quota concurrency, offline/account-switch/deletion; then sandbox/TestFlight and Play license-test purchases/restore/refunds before production. No real purchases are needed for repository design (`__tests__/entitlements.test.ts:53-135`; `docs/compliance/phase5c-payment-architecture.md:210-216`).

Do not add trials, family sharing, detailed billing analytics, a new payment provider, or a broad refactor unless the approved product scope/store integration actually requires them. Supabase Pro is not a prerequisite established by the repository.
