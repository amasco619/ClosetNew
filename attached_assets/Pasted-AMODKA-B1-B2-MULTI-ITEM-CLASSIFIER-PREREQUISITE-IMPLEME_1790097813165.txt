==================================================
B1 — SEPARATE MULTI-ITEM PATH
==================================================

Create a new isolated multi-item classifier path.

It must NOT replace or alter:

POST /api/classify-garment

The legacy endpoint must continue returning its existing scalar ClassificationResult.

The new path must be independently disableable.

Use a clearly separate route/module/feature boundary.

The multi-item result must be an explicit typed envelope.

At minimum, establish types for:

MultiItemClassificationResult

items[]

relationship

validation metadata

Each item must be able to represent:

- stable detection identity
- detection ordering/position
- normalized scalar classification
- item confidence
- source-image provenance sufficient for later B3 use

Relationship metadata must represent:

- relationship type
- relationship confidence
- shared relationship attributes where supported

Use the existing Phase A relationship vocabulary only:

- coordinated_set
- multi_item
- layered

Do not invent additional persisted relationship types.

==================================================
B1 — DETECTION MODEL
==================================================

The multi-item path must distinguish:

1. source image
2. detected garment instances
3. scalar classification of each garment
4. relationship between those garments

Do not represent a multi-item image as one WardrobeItem.

Do not add group fields to WardrobeItem.

Do not persist anything.

The implementation may use an intermediate provider response shape internally, but provider-specific raw data must not leak into the validated public contract.

==================================================
B2 — REUSE EXISTING NORMALIZATION
==================================================

Every detected garment must pass through the existing scalar normalization behavior.

Reuse the existing normalization machinery rather than duplicating category/subtype/colour/attribute rules.

Preserve existing scalar behavior.

Do not alter:

- category allowlist
- subtype normalization
- colour validation
- attribute allowlists
- confidence handling
- derived fields
- colour-signal behavior
- guardrails

B2 adds the envelope around this existing behavior.

==================================================
B2 — ENVELOPE VALIDATION
==================================================

Validate the complete result before exposing it to downstream code.

Required validation:

- items must be an array
- item count must be >= 2 for a multi-item result
- item count must have an explicit maximum
- every item must have a unique detection identity
- every required item must successfully normalize
- malformed item entries must reject the envelope
- unsupported relationship types must reject
- relationship confidence must be valid
- group/member consistency must be valid
- deterministic item ordering must be established
- duplicate detected garments must be rejected
- missing required fields must reject
- malformed envelope must reject
- empty array must reject
- excessive array must reject

Do not silently drop an invalid item and continue with a partial set.

The whole multi-item result must be rejected if required envelope validation fails.

==================================================
SINGLE-ITEM BEHAVIOR
==================================================

Do not change existing single-item behavior.

Single-item images must continue through the existing scalar route.

Do not automatically route existing single-item uploads through the new multi-item path.

The new path must be additive.

==================================================
RELATIONSHIP SEMANTICS
==================================================

Use:

coordinated_set
multi_item
layered

Relationship metadata belongs to the envelope/group layer.

It does not belong inside WardrobeItem.

Do not call create_garment_group().

Do not create groups.

Do not create memberships.

==================================================
DETECTION IDENTITY
==================================================

B1/B2 needs a deterministic detection identity for validation and downstream B3 use.

Do NOT confuse detection identity with the future persistent wardrobe item UUID.

Do not generate the future persistence item UUID here.

Detection identity must only identify detected garment instances within the classification result.

Document exactly how it is generated and why it remains stable within one classifier result.

==================================================
DETERMINISTIC ORDER
==================================================

Establish deterministic ordering of items.

Do not rely solely on provider array order if the provider can return nondeterministic ordering.

Use an explicit deterministic ordering rule based only on validated detection information.

Document the rule.
