# AMODKA — REVENUECAT BILLING IMPLEMENTATION

## Implementation Task — Production-Grade, Cost-Conscious, Narrow Scope

You are implementing the **approved RevenueCat subscription architecture for Amodka**.

This is an existing production-oriented application. **Do not rebuild existing systems, redesign unrelated UI, or perform broad refactors.** Implement only the billing work described below.

The goal is to move Amodka from its currently defined billing contracts into a real, server-authoritative RevenueCat subscription implementation while preserving all existing functionality and protected systems.

# 1. AUTHORITATIVE PRODUCT / BUSINESS MODEL

These decisions are already approved. Do not reinterpret them.

## Free

* Maximum active wardrobe items: **30**
* Daily Outfit Recommendations remain available.
* No Premium entitlement.

## Premium

* Maximum active wardrobe items: **2,000**
* Premium includes everything outside the Free tier.
* Premium is one tier only.
* Monthly and annual subscription products.
* **3-day free trial**, auto-renewing into the selected subscription.
* No introductory/promotional pricing.
* Cancellation preserves Premium access until the provider's effective expiration.
* Expiry preserves all wardrobe data.
* Expiry does NOT delete excess wardrobe items.
* Premium capacity is exactly **2,000 active wardrobe items**.
* Do NOT use or display the phrase **"Unlimited Wardrobe."**
* Premium follows the authenticated Amodka account across iOS and Android.

## Downgrade

Approved Free downgrade model:

**Option B — user-selected 30 ("Choose your 30").**

When Premium expires:

* Existing wardrobe data remains intact.
* The user does not lose/delete excess items automatically.
* The user selects which 30 remain active for Free access.
* No physical copy/delete operation is performed merely because Premium expired.

The existing B2.8 implementation and live Supabase migration already enforce the relevant wardrobe-capacity model. Do not replace it.

# 9. REVENUECAT WEBHOOK

Implement:

`POST /api/billing/revenuecat/webhook`

This endpoint is the server-side ingestion boundary.

Security requirements:

* Verify RevenueCat webhook HMAC.
* Verify the signature against the **raw request body bytes before JSON parsing**.
* Use the RevenueCat signing secret from server-side environment/secrets only.
* Use constant-time signature comparison.
* Parse the `X-RevenueCat-Webhook-Signature` header.
* Validate timestamp freshness/replay tolerance.
* Reject malformed/unsigned/invalid requests.
* Never log the signing secret.
* Never log raw purchase payloads if they contain unnecessary sensitive data.
* Never put RevenueCat provider secrets in client code.

RevenueCat currently documents the signature as:

`t=<unix_timestamp>,v1=<hmac_sha256_hex>`

and computes HMAC-SHA256 over:

`<timestamp>.<raw_json_body>`

The raw body must be preserved before JSON parsing.

Use a sensible replay tolerance consistent with RevenueCat's current guidance (approximately 5 minutes).

The webhook should respond quickly and avoid unnecessary long-running work in the request path. RevenueCat documents retries for non-2xx responses, so the endpoint must be idempotent.

---

# 10. WEBHOOK IDEMPOTENCY

RevenueCat webhook delivery is not guaranteed to be exactly-once.

Use the existing approved billing event-journal architecture.

Persist a deterministic unique RevenueCat event identifier.

Repeated delivery of the same event must NOT:

* duplicate transactions,
* duplicate subscription rows,
* extend Premium twice,
* revoke Premium incorrectly,
* create duplicate ledger records,
* corrupt entitlement state.

If an event was already successfully processed:

* acknowledge it safely,
* do not perform the business operation twice.

If processing fails after event receipt:

* preserve enough durable state to retry/reconcile safely.

Do not delete a billing event merely because processing failed.

* Premium remains active until the authoritative provider expiration date.

When Premium actually expires:

* entitlement becomes inactive,
* wardrobe data remains,
* excess wardrobe items remain stored,
* Free capacity becomes 30,
* existing B2.8 Free selection logic applies,
* user can choose their 30.

Do not delete wardrobe items during expiry processing.

Do not physically copy wardrobe items into a new table.

Do not automatically delete the user's excess wardrobe.
