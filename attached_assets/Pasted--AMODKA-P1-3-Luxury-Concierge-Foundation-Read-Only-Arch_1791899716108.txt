# AMODKA P1.3 — Luxury Concierge Foundation
## Read-Only Architecture & Implementation-Contract Audit

### Objective

Design a practical, implementation-ready contract for introducing the Amodka Luxury Concierge foundation into the existing production codebase.

Amodka's positioning is:

**“A quiet-luxury stylist in your pocket.”**

The long-term experience should feel like an elite celebrity personal stylist and luxury fashion concierge, serving women first, with Nigerian and broader African fashion treated as first-class rather than peripheral.

This task is strictly **READ-ONLY**. Inspect the current implementation and produce an evidence-based architecture and implementation contract. Do not implement the feature.

### 1. Inspect the existing architecture

Inspect only the files and flows necessary to understand:

- App navigation, tabs, screen conventions and existing premium UI components.
- Existing outfit-generation and styling flows.
- Canonical wardrobe semantics and `projectWardrobeForStyling()`.
- Phase A garment groups and the relationship-aware Traditional styling pipeline.
- Weather retrieval, temperature preferences and weather-aware recommendations.
- Authentication, user-specific data access, premium entitlements and existing purchase/subscription gates.
- Existing loading, empty, error, retry and offline/degraded states.
- Relevant tests, technical documentation and product notes.

Start with a narrow file map. Follow actual imports and call sites before drawing conclusions. Do not perform an indiscriminate whole-repository audit.

### 2. Define the product boundary

Treat Luxury Concierge as a future umbrella experience that can eventually support:

- **Today:** a useful, personalized outfit recommendation.
- **Wardrobe:** the user's owned garments and confirmed relationships.
- **Stylist:** existing outfit and occasion styling capabilities.
- **Concierge:** guided planning for trips, events, occasions and capsule wardrobes.
- **Discover/Shop:** a possible later commerce extension.

These are product concepts, not instructions to create five new tabs or redesign the current navigation. Recommend the smallest coherent first release that fits the existing application.

P1.3 should establish the Concierge foundation, not deliver the full Packing/Travel Capsule Concierge.

### 3. Answer the critical architecture questions

For each answer, cite the relevant existing files, functions or tests.

1. What existing screen, navigation entry point or interaction should host the first Concierge experience, and why?
2. What is the smallest genuinely useful Concierge journey that can be delivered without duplicating existing outfit generation?
3. Which existing services, components, types and persistence mechanisms can be reused directly?
4. What new concepts or data structures are actually necessary for the foundation?
5. Can the first release work without a new database schema, external AI provider, new recommendation engine or new subscription product?
6. How should Concierge use canonical user-confirmed wardrobe semantics and confirmed Phase A relationships?
7. How should it respect the existing Traditional styling path and African-fashion representation?
8. How should weather and the global Celsius default be incorporated without duplicating weather logic?
9. How should authentication, entitlement checks, user ownership, privacy and degraded states be handled?
10. Which parts belong in P1.3, which belong in P1.4 Packing/Travel Capsule Concierge, and which should be deferred?

Clearly distinguish verified existing capabilities from proposed capabilities and unverified assumptions.

### 4. Establish a minimal first-release experience

Recommend one concrete first-release Concierge journey. It must provide user value, use the user's actual wardrobe where applicable, and have an honest outcome when there is insufficient wardrobe data.

Evaluate whether a guided occasion-planning experience is a better foundation than a free-form chat interface. Do not add an LLM conversational layer merely because the product is called Concierge.

The proposed foundation should be:

- Visibly premium and consistent with Amodka's existing quiet-luxury design language.
- Guided, understandable and useful on mobile.
- Grounded in the user's actual wardrobe and confirmed garment relationships.
- Explicit about missing information rather than inventing garment attributes or ownership.
- Capable of handling African, Western and mixed-fashion contexts where the existing styling capabilities support them.
- Designed to extend into P1.4 without building P1.4 prematurely.

Do not prescribe a new visual redesign unless inspection identifies a concrete blocker.

### 5. Define the architecture contract

Specify:

- User journey and screen states.
- Data flow from user intent to existing styling services and back to the UI.
- Clear ownership of responsibilities between UI, orchestration and existing styling modules.
- Any minimal new interfaces or types, with proposed locations.
- Whether any state must persist, and why.
- Loading, empty, insufficient-wardrobe, failure, retry and stale-response behavior.
- Authentication and entitlement boundaries.
- Privacy and data-minimization requirements.
- Accessibility and mobile-layout considerations.
- How to avoid duplicate recommendation logic and preserve the existing source of truth.

Do not introduce new database tables, persistent trip records, a new AI provider or a second recommendation engine unless the audit demonstrates that the foundation cannot work without them. If any are proposed, explain the concrete requirement they satisfy and offer the simpler alternative.

### 6. Frozen and protected areas

The following are non-negotiable:

- Recommendation Engine v3.7 remains frozen.
- Do not modify its scoring, ranking, candidate generation, affinity, rotation, weather decision logic or benchmark expectations.
- Do not rebuild existing wardrobe, Traditional styling, weather, authentication, entitlements or Phase A garment-group functionality.
- Do not change existing production schemas or migrations.
- Do not modify providers, secrets, environment configuration or production data.
- Do not implement packing lists, travel-date orchestration, destination weather aggregation, commerce recommendations, virtual try-on, notifications or subscriptions as part of this task.
- Do not change files. No code edits, migrations, package changes, provider calls, production queries or benchmark reruns.

Read-only local inspection and reading existing tests/documentation are permitted.

### 7. Implementation sequencing

Propose a short, dependency-aware implementation sequence:

- P1.3 foundation: the smallest usable Concierge experience.
- P1.4: Packing/Travel Capsule Concierge, only after the foundation is approved.
- Any later phases justified by explicit requirements.

For each proposed implementation step, identify its objective, likely files, dependencies, focused tests and stop condition. Separate launch-critical requirements from optional polish.

Keep the plan economical: reuse existing architecture and avoid broad refactors.

### 8. Required output

Return a concise but evidence-rich report containing:

1. Executive recommendation and verdict.
2. Relevant existing architecture and source-of-truth file map.
3. Verified capabilities, gaps and assumptions.
4. Recommended first-release user journey.
5. Proposed architecture and data-flow contract.
6. Proposed file-level change plan for P1.3.
7. Explicit P1.3 versus P1.4 scope boundary.
8. Security, privacy, entitlement and failure-state requirements.
9. Targeted validation plan and acceptance criteria.
10. Risks, unresolved decisions and the smallest next implementation prompt.

Reference actual files, functions, tests and types wherever possible. If something cannot be verified from the repository, state that limitation explicitly.

### Stop condition

This is an audit and specification task only. Make **zero file changes** and perform no production mutations. Stop after delivering the report and proposed implementation contract. Do not begin implementation or silently expand scope.
