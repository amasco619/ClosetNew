# Amodka — Read-Only Onboarding Personalization Audit

## Objective

Determine whether every personalization field collected during onboarding is genuinely consumed by Amodka’s live outfit styling and recommendation pipeline, and identify which fields or options are unused, partially used, or merely stored.

This is a **diagnostic-only task**. Produce an evidence-based report from the current codebase. Do not implement changes.

## 1. Trace each onboarding field end to end

Investigate these exact fields:

1. Body shape
2. Face shape
3. Eye colour
4. Skin tone
5. Skin undertone
6. Style goals

For each field, trace the actual path through:

- Onboarding UI and selected option values
- State management and profile persistence
- Profile hydration when the app starts or the user signs in
- Request construction and context passed to outfit generation
- Recommendation Engine v3.7 and any upstream or downstream styling logic
- Candidate generation, eligibility filtering, scoring, ranking, and final outfit selection
- Any AI prompt used to generate or refine outfit recommendations

Identify the actual files, functions, and field names involved at each boundary.

## 2. Classify real usage, not apparent usage

For every field, assign one of these evidence-based statuses:

- **Engine-consumed:** demonstrably affects recommendation-engine logic or its inputs in a way that can change outfit results.
- **AI-prompt-consumed:** passed to an AI prompt but not demonstrably consumed by engine logic.
- **Stored/displayed only:** persisted or shown in the UI but does not reach the active styling path.
- **Collected but dropped:** collected during onboarding but lost before reaching styling.
- **Conditional:** used only under a specific condition; explain the condition and actual effect.
- **Unverified:** code evidence is insufficient to establish runtime use.

A field appearing in a TypeScript interface, database table, prompt template, or profile screen is not proof that it influences recommendations. Trace the consumer.

## 3. Inspect every style-goal option

Enumerate the actual style-goal options shown to users in onboarding.

For each option, determine whether it:

- Maps to a concrete recommendation rule, filter, score, or ranking signal
- Changes the candidate pool or outfit composition
- Is passed only as descriptive text to an AI prompt
- Is stored but never consumed
- Is normalized or mapped incorrectly, or silently ignored

Do not assume every option is supported just because the UI offers it.

## 4. Assess personalization effectiveness

Determine whether the existing code can demonstrably produce different recommendations when only one profile field changes while the wardrobe, weather, occasion, and other inputs remain constant.

Use static tracing and existing offline tests or fixtures where available. Do not call paid AI providers or run provider-backed generation.

Distinguish carefully between:
- Code evidence that a field influences results
- Existing test evidence
- Runtime behavior that remains unverified

Do not invent numerical personalization metrics or claim that recommendations differ unless the evidence supports it.

## 5. Required report

Provide:

1. An executive summary stating whether onboarding personalization is fully, partially, or minimally wired into recommendations.
2. A table covering all six fields, with collection, persistence, hydration, recommendation-path usage, actual effect, evidence, and status.
3. A complete list of style-goal options and their actual implementation status.
4. Any profile-field mismatches, dropped values, dead mappings, conditional paths, or inconsistent naming.
5. Which onboarding answers currently have no demonstrable influence on recommended outfits.
6. The smallest, safest implementation opportunities, prioritized by user impact and confidence.
7. The offline tests needed to prove each proposed change.

## 6. Strict protections

- READ-ONLY: do not modify any code, prompt, database, schema, configuration, test, fixture, or documentation.
- Do not change Recommendation Engine v3.7, its scoring, candidate generation, ranking, or weather logic.
- Do not modify Track B/C benchmark artifacts or frozen evaluation data.
- Do not perform provider-backed generation or incur paid API costs.
- Do not run migrations or change Supabase.
- Do not publish or deploy.
- Do not implement proposed fixes during this task.

Preserve all protected systems. Stop after delivering the evidence-based report.
