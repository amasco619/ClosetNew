# P1.4-A — Travel Capsule Candidate-Source Clarification

This is a narrowly scoped, READ-ONLY follow-up to the completed P1.4 architecture audit.

Do not implement the travel feature. Do not change any files, run migrations, add dependencies, modify providers, run broad test suites, or alter Recommendation Engine v3.7, Phase A, daily rotation, wear history, or existing styling behaviour.

## Objective

Resolve one implementation-blocking uncertainty: **How will the proposed travel planner obtain suitable selectable outfits for each activity using existing, safe public code paths?**

The previous audit established that `AppContext` exposes `outfitPool` and `outfitSets`, but described the latter as selected results rather than a dedicated trip-planning candidate pool. The proposed implementation then relies on the current selected catalogue.

Do not assume those are interchangeable.

## Required investigation

1. Trace how `outfitPool` and `outfitSets` are constructed, filtered, selected, and updated in `contexts/AppContext.tsx` and the relevant rotation/scenario code.

2. Establish whether the currently exposed results contain:
   - Multiple selectable looks for each supported activity.
   - Scenario identity that can be reliably matched to an activity.
   - Stable wardrobe-item identities suitable for ownership validation and checklist derivation.
   - Complete enough component information to identify selected garments and relevant confirmed coordinated-set membership.

3. Determine whether any existing public service can safely supply scenario-specific choices without:
   - Changing v3.7.
   - Simulating future dates.
   - Mutating daily rotation, wear history, mood, reactions, or saved looks.
   - Bypassing normal eligibility, ownership, or set safeguards.
   - Reconstructing a hidden engine pool through an unsupported workaround.

4. Explain how the existing Traditional styling pathway can supply choices alongside generic scenarios without falsely claiming that generic scenarios have equivalent relationship-aware construction.

5. Identify the consequences of a finite or incomplete candidate catalogue. For example, can a user legitimately plan four days of different activities if only one or two relevant looks are currently selectable?

## Required output

Provide:

- Exact file paths and function/type names supporting each finding.
- The verified data flow from existing recommendation results to a potential day-slot selection.
- A table distinguishing **verified capability**, **unsupported assumption**, and **remaining limitation**.
- One recommendation:
  A. use existing selected results and explicitly accept limited availability;
  B. reuse an existing safe public scenario-specific path, naming it and explaining its side effects; or
  C. stop and seek a separate architecture decision because neither approach supports a trustworthy MVP.
- Updated acceptance criteria for candidate selection, ownership, scenario matching, and empty slots.
- A concise statement of what remains safe to implement if the catalogue is incomplete.

Do not invent new functions or describe proposed functions as if they already exist.

## Stop condition

Stop once the candidate-source question is resolved. No implementation, no unrelated audit expansion, and no test claims unless tests were actually run.

Confirm that no files, configuration, database objects, or protected styling behaviour were changed.
