P1.1 — Traditional Styling Context: First Real African Styling Capability

Objective
Make Amodka's existing "Traditional" styling experience genuinely functional and user-visible.

Traditional must become a real styling context that influences wardrobe candidate selection/assembly through the existing Styling Intelligence boundary, while preserving Recommendation Engine v3.7 unchanged.

This is the first visible African styling capability built on P0.1 + P0.2.

Existing implementation
- P0.1 canonical wardrobe semantics is complete and production-validated.
- P0.2 canonical wardrobe → Styling Intelligence boundary is complete and production-validated.
- Phase A garment groups are production-approved.
- Recommendation Engine v3.7 is FROZEN.
- African taxonomy is already implemented.
- Existing Traditional UI/model concepts already exist.
- The African Fashion Capability Audit and Stylist Independence Audit are the source of truth.
- Do not perform a whole-repository audit.

Product requirement

When a user chooses a Traditional styling context, Amodka must actually use that context when constructing recommendations.

Do NOT merely:
- rename a label
- add a Traditional badge
- expose an unused scenario
- hard-code a fixed outfit
- create a second recommendation engine

Traditional must affect the styling decision pipeline.

Architecture

Use this flow:

User selects Traditional context
        ↓
Styling context / intent
        ↓
Canonical wardrobe + Phase A relationships
        ↓
Deterministic Traditional styling adapter
        ↓
Existing candidate generation / v3.7 evaluation
        ↓
Traditional-aware recommendation

Keep v3.7 itself unchanged.

The adapter/context layer is responsible for expressing Traditional requirements to the existing styling machinery. v3.7 remains responsible for its proven compatibility/scoring/ranking behaviour.

Scope of Traditional context

Implement only what the existing data and audits support confidently.

Traditional should be represented as a USER-SELECTED STYLING CONTEXT, not as an inferred property of a garment.

Do not infer from:
- garment subtype alone
- colour
- fabric
- African origin
- AI confidence
- garment name

Examples:
- A buba does not automatically mean the user is attending a traditional event.
- A wax-print garment does not automatically mean Traditional.
- A gele does not automatically make every outfit Traditional.

User intent/context is authoritative.

African wardrobe semantics

Preserve existing supported concepts, including:
- buba
- iro
- wrapper
- iro-and-buba
- boubou
- aso-ebi
- gele
- headwrap
- head-scarf
- structured-headpiece
- wax-print
- lace/chiffon
- kaftan

Do not expand the taxonomy during this task.

Traditional compatibility must prefer appropriate canonical African garment semantics where available, but MUST NOT assume cultural requirements that are not represented.

Do not claim that every Traditional outfit requires:
- gele
- aso-ebi
- wrapper
- matching print
- a particular fabric
- a particular colour

These are context-dependent and should remain optional unless explicitly represented by user intent/data.

Relationship handling

Consume existing Phase A relationships through the P0.2 styling boundary.

Where a confirmed coordinated_set exists:
- preserve the relationship
- do not split it into unrelated styling candidates merely because individual pieces could technically be paired separately

Where layered relationships exist:
- preserve their relationship information
- do not invent layer order if it is not represented

Do not rebuild Phase A groups.

Do not introduce a second relationship model.

Candidate behaviour

Traditional context should influence candidate eligibility/assembly in a deterministic, explainable way.

At minimum:
- avoid treating Traditional context as equivalent to generic casual
- avoid recommending obviously incompatible generic combinations when stronger Traditional-compatible wardrobe options exist
- preserve confirmed coordinated African sets where appropriate
- preserve individual garment truth
- do not fabricate missing garments
- do not silently substitute garments the user does not own

If the wardrobe is insufficient for a strong Traditional recommendation:
- return the best valid wardrobe-aware result available
- expose the relevant wardrobe gap through existing gap mechanisms where supported
- do not fabricate a complete outfit

Do not create a new recommendation-ranking algorithm.

Do not add hidden LLM reasoning.

Do not call Gemini or any external AI provider.

Traditional + Western wardrobe

A Traditional context does NOT mean all Western garments become forbidden.

The adapter should allow appropriate African + Western combinations when the canonical semantics and existing compatibility machinery support them.

Do not assume "African-only" unless that intent already exists explicitly.

Do not introduce a new African-only toggle in this task.

Formality

Respect canonical user-confirmed formality where available.

Do not globally change v3.7 subtype-formality precedence.

Do not rewrite existing formality logic.

Traditional context may narrow/guide candidate suitability, but must not falsify garment formality.

Weather

Use the existing weather inputs and v3.7 weather behaviour.

Do not modify v3.7 weather logic in this task.

Do not introduce the Celsius fix in this task.

Cultural claims

Do not encode unsupported claims such as:
- "this is Nigerian wedding appropriate"
- "this is Yoruba traditional wear"
- "this is Igbo traditional wear"
- "this fabric is culturally required"
- "this headpiece is mandatory"

unless the existing canonical data explicitly supports such a distinction.

This phase is Traditional styling context, not cultural-authenticity classification.

UX

Make the existing Traditional option visibly meaningful.

The user should be able to:
1. choose Traditional styling
2. understand what the context means
3. generate/retrieve recommendations
4. see recommendations that actually differ when Traditional compatibility materially changes the candidate set

Keep the UX premium and restrained.

Do not redesign the entire styling screen.

Use the existing Amodka design language.

If helpful, provide a concise contextual description such as:
"Style from your wardrobe with an African-first traditional occasion in mind."

Do not use culturally presumptive copy.

If the current UI exposes Traditional but routes it through a generic scenario list, connect the existing control to the real context rather than creating a duplicate control.

Important: do not add a new settings screen.

Visible product proof

Add a focused test/fixture demonstrating that Traditional context is actually consumed.

The test must prove more than:
"traditional-event exists."

It should demonstrate that the Traditional context reaches the candidate-selection/assembly boundary and can change the resulting eligible recommendation set where the fixture contains materially different candidates.

Use deterministic fixtures.

Do NOT alter frozen benchmark cases.

Tests

Add focused tests covering:

1. Traditional context is explicitly user-selected.
2. Traditional context reaches the Styling Intelligence boundary.
3. Traditional context is NOT inferred from garment subtype.
4. Existing African canonical semantics remain intact.
5. Confirmed coordinated_set relationships remain intact.
6. Traditional context can change candidate eligibility/assembly when appropriate.
7. Traditional does not fabricate missing wardrobe items.
8. Traditional does not invoke Gemini/provider APIs.
9. Traditional does not mutate canonical wardrobe data.
10. Equivalent canonical wardrobe data produces deterministic results.
11. Existing generic styling behaviour remains unchanged when Traditional context is not selected.
12. Frozen v3.7 output remains unchanged for existing non-Traditional fixtures.

Regression

Run:
- focused Traditional tests
- relevant P0.1/P0.2 semantic tests
- relevant group/relationship tests
- typecheck
- relevant lint
- git diff --check

Run the existing frozen v3.7 golden regression if the integration touches its input boundary.

Expected invariant:
Existing non-Traditional v3.7 fixtures must remain byte/result equivalent.

Database

Prefer NO migration.

Do not add persistent Traditional fields to wardrobe_items.

Traditional is context/intent, not a garment attribute.

Only introduce persistence if the existing product flow already requires the user's selected styling context to survive navigation/reload. If persistence is required, reuse the existing context/preferences architecture rather than adding a new wardrobe column.

Protected areas

DO NOT modify:
- v3.7 scoring
- v3.7 ranking
- v3.7 candidate-generation algorithms
- affinity/pair-affinity algorithms
- weather algorithms
- rotation algorithms
- benchmark definitions
- Track B
- Track C
- Phase A migrations/RLS/security
- canonical wardrobe persistence
- P0.2 semantic adapter contract
- Gemini/provider behaviour
- African taxonomy
- authentication
- entitlement/payment logic
- Concierge
- Packing
- Celsius/weather-unit work

Implementation discipline

Before editing, inspect only the specific files required to trace:
- current Traditional UI/control
- scenario/context representation
- P0.2 styling boundary
- candidate eligibility/assembly entry point
- existing relevant tests

Then make the smallest coherent implementation.

Reuse existing architecture.

Do not refactor unrelated code.

Do not create a parallel styling pipeline.

STOP CONDITION

Stop when:
- Traditional is a real user-selected styling context
- it reaches Styling Intelligence
- it materially influences candidate eligibility/assembly in a deterministic way
- at least one controlled fixture proves the difference
- non-Traditional behaviour remains unchanged
- tests/typecheck/regression pass

Do NOT continue into:
- Traditional cultural subtypes
- Nigerian wedding/church-specific modes
- aso-ebi role modelling
- required headwear
- African-only mode
- African+Western intent modelling
- new taxonomy
- cultural authenticity detection
- Concierge
- Packing
- recommendation-engine tuning

Final report must contain only:

1. Implemented
2. User-visible Traditional behaviour
3. Styling-context/adapter behaviour
4. Files changed
5. Database changes
6. Tests/validation
7. Frozen/protected areas confirmed unchanged
8. Blockers

Success criterion

A user can select Traditional in Amodka and receive a genuinely Traditional-aware wardrobe recommendation through the Styling Intelligence layer, rather than Traditional being a UI-only label or generic scenario alias.

The implementation must demonstrate this with a deterministic controlled fixture while leaving the proven v3.7 engine unchanged.
