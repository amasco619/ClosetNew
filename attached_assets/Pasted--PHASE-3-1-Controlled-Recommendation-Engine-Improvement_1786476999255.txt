# 4. P0-A — FIX THE WEAR HISTORY / FRESHNESS CONFLICT

## Problem

The Phase 3 audit identified an architectural conflict:

`wornHistoryBoost` increases an outfit's score based on previous wear, while `applyFreshnessOrder()` attempts to move recently worn outfits down.

Subsequent score-based sorting can undo that freshness ordering.

The result can be:

> An outfit that the user wore recently receives a large score boost and resurfaces despite the system intending to prioritise fresh alternatives.

This is a real recommendation-quality problem.

---

## Desired behaviour

We want to preserve two different concepts:

### Preference memory

If the user has repeatedly worn/loved an outfit, that is valuable information.

### Freshness

That does NOT mean the same exact outfit should repeatedly appear immediately after being worn.

The desired principle is:

> **Remember what the user likes, but don't confuse liking something with wanting to see it again immediately.**

---

## IMPORTANT: DO NOT simply copy the Phase 3 suggested numbers

The Phase 3 report suggested examples such as:

* −5 within 2 days;
* −3 within 4 days.

These are illustrative only.

**Do not blindly implement those exact values.**

Before choosing the freshness adjustment, inspect the actual score distribution in the current engine.

Determine:

* typical `rawTotal` ranges;
* typical `wornHistoryBoost` values;
* typical reaction adjustments;
* typical differences between top-ranked candidates;
* how many points are generally required to move an outfit between ranking tiers.

The freshness mechanism should be strong enough to prevent recent repetition but not so strong that it systematically suppresses genuinely excellent outfits.

---

## Preferred implementation principle

Freshness should ultimately participate in the same ranking mechanism that determines final order.

Avoid relying on a positional reorder that is subsequently undone by another score-based sort.

However, preserve the distinction between:

### Recommendation quality

and

### freshness.

Do not simply destroy the existing wear-history signal.

---

## Important edge cases

Explicitly test:

### Case 1 — Never worn

No freshness penalty.

### Case 2 — Worn yesterday

Should be meaningfully deprioritised unless the pool has very poor alternatives.

### Case 3 — Worn several days ago

Should receive a smaller freshness effect.

### Case 4 — Worn weeks ago

Freshness should have little or no negative effect.

### Case 5 — Loved + recently worn

The love signal should remain valuable, but recent wear should still prevent automatic resurfacing.

### Case 6 — Loved + old

A previously loved outfit that has not been worn recently should be allowed to rank highly.

### Case 7 — Only viable outfit

If the wardrobe has no reasonable alternatives, freshness must NOT cause the engine to produce a materially worse outfit simply to avoid repetition.

### Case 8 — Recently worn but substantially better than alternatives

Freshness should not blindly eliminate the best available outfit.

The engine should prefer:

> **excellent + reasonably fresh**

over:

> **poor + technically fresh**

---

## Preserve

Do not remove or weaken:

* item affinity;
* pair affinity;
* reaction learning;
* positive wear history;
* hero diversity;
* cross-scenario deduplication;
* tiered shuffle;
* existing cold-start behaviour.

# 5. P0-B — INTEGRATE `rise` INTO PROPORTION INTELLIGENCE

## Problem

The Phase 3 audit established that `rise` is already captured and stored but is not currently consumed by the recommendation engine.

This is a genuine data-utilisation gap.

Examples:

* high-rise + tucked/slim top can create strong waist definition;
* high-rise + crop top can materially change perceived proportions;
* low-rise + crop can create a very different silhouette;
* rise interacts with wide-leg, slim, oversized and tailored bottoms.

---

# IMPORTANT: DO NOT TURN THIS INTO RIGID FASHION RULES

Do NOT implement simplistic rules such as:

> "high-rise = good"

or:

> "low-rise = bad"

or:

> "high-rise + slim top always gets +1."

Rise is a **contextual proportion signal**.

It interacts with:

* body type;
* height;
* top silhouette;
* bottom silhouette;
* crop length;
* tucked/untucked state if available;
* overall silhouette;
* occasion/style intent.

The implementation should therefore be conservative and additive.

---

## First inspect available data

Determine exactly what values `rise` can contain.

For example, verify whether the actual system uses:

* `high`
* `mid`
* `low`
* `unknown`

or other values.

Do not invent new values.

Determine whether the system captures any additional top-length/tuck information that can safely interact with rise.

If that information does not exist, **do not pretend it does**.

---

# Desired implementation philosophy

`rise` should provide an additional proportion signal rather than becoming a dominant factor.

The rule should:

* improve obviously strong proportion combinations;
* mildly penalise genuinely problematic combinations;
* remain neutral when insufficient information exists;
* never override strong evidence from the rest of the outfit;
* avoid discriminating against a valid fashion choice simply because it is unconventional.

---

# Body-type and height interaction

Evaluate how rise can safely interact with the existing:

* `bodyTypeProportion`;
* `heightProportion`;
* `proportionBalance`.

Avoid duplicating the same bonus across multiple functions.

For example, do not accidentally create:

`rise bonus + body-type rise bonus + height rise bonus`

that produces an artificial large score advantage.

The combined influence of rise should remain modest relative to major signals such as:

* occasion;
* style goal;
* formality;
* colour harmony;
* overall outfit coherence.

---

# Unknown/missing rise

This is critical.

Legacy wardrobe items may have:

* `rise = undefined`;
* missing metadata;
* values that the current system doesn't recognise.

These items must continue to work.

Unknown rise should mean:

> **No rise-based adjustment**

not:

> **Penalty**

and not:

> **Assume mid-rise**

unless the current code already explicitly defines that behaviour.
