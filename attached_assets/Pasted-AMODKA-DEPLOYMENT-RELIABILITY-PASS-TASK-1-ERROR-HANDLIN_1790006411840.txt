AUDIT OBJECTIVES
==================================================

A. MAP THE CURRENT ERROR ARCHITECTURE

Identify and document:

- root application layout
- ErrorBoundary implementation
- ErrorFallback implementation
- AmodkaErrorState implementation
- existing error types/classes
- API/network error handling
- Supabase error handling
- authentication error handling
- upload error handling
- wardrobe/add-item error handling
- outfit-generation/recommendation error handling
- profile error handling
- sign-out error handling
- account deletion error handling
- onboarding error handling
- migration/bootstrap error handling
- startup/font/loading state handling
- splash-screen lifecycle
- navigation-level error handling
- async operation handling
- retry mechanisms
- alert/toast/modal error mechanisms

Build a concise map of where errors currently flow.

B. FIND SILENT FAILURE PATHS

Search the codebase for patterns such as:

- empty catch blocks
- console-only error handling
- swallowed Promise rejections
- catch blocks that return fallback values without recording the failure
- async operations whose failures are ignored
- fire-and-forget promises
- loading states that can remain permanently active
- state transitions that can leave the UI stuck
- navigation flows that can fail without user feedback
- startup operations that can prevent the app from becoming usable

Do not automatically classify every console.error as a defect.

For each finding explain:

- file
- function/component
- failure scenario
- current behaviour
- user-visible consequence
- whether recovery currently exists
- severity
- recommended treatment

C. STARTUP / SPLASH RELIABILITY

Trace the complete startup sequence.

Determine:

1. What happens from native launch to first usable screen?
2. Which asynchronous operations must complete before the app becomes usable?
3. Which operations can fail?
4. What happens when each fails?
5. Can any operation indefinitely prevent startup?
6. Is there a timeout?
7. Is there a fallback?
8. Can the user retry?
9. Can the user continue in a degraded/offline state?
10. Can the app become permanently stuck on the splash/loading state?

Document the actual control flow.

Do not redesign startup.

D. OFFLINE / NETWORK FAILURE

Audit how the app behaves when:

- there is no internet connection
- connection drops during an API request
- connection drops during image upload
- connection drops during authentication
- connection drops during profile loading
- connection drops during wardrobe loading
- connection drops during outfit generation
- a request times out
- Supabase is temporarily unavailable
- an external API fails
- an external API returns malformed/unexpected data

Determine which flows already have recovery behaviour and which do not.

Do not introduce an offline architecture at this stage.

E. USER-FACING ERROR UX

Audit consistency of error presentation.

Determine where the app currently uses:

- Alert
- Toast
- Modal
- Inline error
- AmodkaErrorState
- ErrorFallback
- Retry button
- Navigation fallback
- Silent recovery
- Console-only reporting

Determine whether the same class of failure is presented consistently across the app.

Pay particular attention to whether the UX communicates:

- what happened
- whether the user's data is safe
- what the user can do next
- whether retrying is appropriate
- whether the failure is temporary
- whether the user should leave/restart the flow

Do NOT redesign the visual system.

F. OBSERVABILITY

Determine exactly what production observability currently exists.

Inspect for:

- Sentry
- Bugsnag
- Firebase Crashlytics
- Expo Application Services crash/error facilities
- custom logging
- analytics events
- server-side logging
- Supabase logging dependencies
- structured error logging

Do not install or recommend a specific vendor yet.

If observability is absent or incomplete, document what minimum capability is required for launch and what information it should capture.

Pay special attention to avoiding:

- passwords
- access tokens
- refresh tokens
- authorization headers
- signed Storage URLs
- personal data
- wardrobe image contents
- sensitive profile data
- raw database credentials
- secrets

G. ERROR CLASSIFICATION

Determine whether the current application has a coherent distinction between categories such as:

- validation error
- authentication error
- authorization error
- network error
- timeout
- server error
- dependency/external API failure
- upload failure
- database failure
- unexpected programming error
- unavailable/offline state

If classification is inconsistent, document the minimum architecture needed to make it consistent.

Do not implement it.

H. RECOVERY SEMANTICS

For each important user flow, determine whether the correct response to failure is:

- retry
- retry after connection restored
- return to previous screen
- restart the operation
- reload data
- abandon operation
- show degraded state
- show support/contact path
- terminate the flow safely

Do not invent behaviour.

Base recommendations on the existing flow and its data-safety characteristics.

I. DATA SAFETY

Specifically identify operations where a failed request could potentially result in:

- duplicate records
- duplicate uploads
- partially completed operations
- stale local state
- inconsistent UI state
- lost user input
- repeated side effects

This is an audit only.

Do NOT implement idempotency or persistence changes.

If such a risk intersects with the approved B0.3 architecture, flag it explicitly as a future dependency rather than changing it.
