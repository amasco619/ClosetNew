TRACK C — PREMIUM WARDROBE EXPERIENCE

This is one of the most important visual changes.

Current issue

Garment tiles currently use the garment's primary colour as the major background treatment.

This is visually interesting but can become:

noisy;
inconsistent;
less premium as the wardrobe grows;
more like an inventory catalogue than a luxury digital wardrobe.

We want the garment itself to become the visual hero.

C1. New wardrobe tile philosophy

Use:

clean garment + quiet neutral canvas + restrained metadata

The background should generally be a consistent premium neutral.

Do NOT use a different saturated background for every garment.

C2. Primary colour becomes an accent

Do not discard primary-colour information.

Instead use it subtly through:

tiny colour indicator;
accent line;
metadata dot;
restrained visual cue.

The garment itself should remain dominant.

C3. Garment presentation

Where a processed/background-removed garment image is available:

centre it;
give it generous breathing room;
maintain consistent visual scale;
use subtle shadow/depth;
preserve garment proportions;
avoid aggressive cropping;
avoid unnecessary borders.

The wardrobe should feel like:

a private luxury showroom

rather than:

a database of uploaded photographs.

C4. Metadata

Keep metadata restrained.

Example:

Cashmere Knit

Cashmere · Cream

Avoid excessive badges.

The user should understand the garment at a glance.

C5. Image consistency

Different source photos will have wildly different:

lighting;
framing;
garment scale;
camera angles.

Create a consistent presentation layer.

Do NOT distort garments.

If necessary:

calculate aspect ratio;
use object-fit/contain equivalent;
establish safe visual bounds;
normalise presentation scale.
C6. Loading state

Do not show ugly generic skeletons if they conflict with the premium design.

Consider a restrained:

soft neutral placeholder + subtle shimmer

while the garment image loads.

TRACK D — PHOTOROOM → GEMINI PIPELINE

This is an architectural improvement that must be implemented carefully.

Desired flow
User image
    ↓
PhotoRoom background removal
    ↓
Clean garment image
    ↓
Gemini garment analysis
    ↓
Structured metadata
    ↓
Supabase wardrobe record
    ↓
Amodka recommendation engine

Gemini must remain:

garment perception / metadata enrichment

not:

outfit ranking.

D1. Do not blindly migrate

Before changing the production flow:

Create a small comparison benchmark.

Compare:

Pipeline A

against:

Pipeline B

PhotoRoom-cleaned image → Gemini

Evaluate representative garments across:

subtype;

confidence;

D2. Decision rule

Only adopt the PhotoRoom → Gemini pipeline if it demonstrates a meaningful improvement or operational advantage.

If results are equivalent or worse:

do not force the migration.

Document the result.

D3. Failure handling

The pipeline must tolerate:

PhotoRoom failure

Do not destroy the original garment.

Gemini failure

The garment must not disappear.

Timeout

Gracefully retry according to existing safe retry policy.

Malformed Gemini response

Validate before persistence.

Missing metadata

Persist valid fields and leave unsupported fields null/default according to the existing schema.

Do not invent metadata.

D4. Data preservation

Always preserve:

original uploaded image;
processed image where applicable;
garment metadata;
ownership;
timestamps.

Do not make the original image unrecoverable simply because the processed version exists.

D5. Cost awareness

Measure:

PhotoRoom latency;
Gemini latency;
calls per garment;
failure/retry count.

Do not create accidental duplicate AI calls.

The target architecture should be:

one controlled enrichment operation per garment, with caching/idempotency where appropriate.

TRACK E — GRACEFUL ERROR HANDLING

Create a consistent error-handling experience.

Do NOT simply expose:

Error 500

or:

Something went wrong.

Different failure types should communicate differently.

E1. Recommendation failure

Use language such as:

We couldn't curate a look right now.

Your wardrobe is safe. Please try again.

Provide a clear action.

E2. Legitimate wardrobe gap

Do NOT call this an error.

Use the wardrobe-intelligence experience described in Track F.

E3. Garment classification failure

Example:

We couldn't identify this piece just yet.

Your photo is safe. You can try again or review the details manually.

E4. Background-removal failure

Example:

We couldn't prepare this garment image.

Let's try processing it again.

E5. Network failure

Example:

You're currently offline.

Your saved wardrobe remains available.

Do not imply that the user's wardrobe has been lost.

E6. Generic fallback

Create a reusable error component/system so error states remain visually and linguistically consistent.

TRACK F — COLD/RAIN WARDROBE GAP INTELLIGENCE

This should now become a product feature, not an error state.

The recommendation engine must remain unchanged.

The product layer interprets a legitimate inability to construct an outfit.

F1. Detect the existing condition

Use the existing recommendation engine's output.

Do NOT create a parallel scoring system.

If the engine correctly determines:

no valid outfit can be constructed under the current constraints/context

the UI should explain why.

F2. Example

For cold/rain conditions:

Your wardrobe needs one more layer.

Today's weather is cold and wet, but your wardrobe doesn't currently contain a suitable warm waterproof outer layer.

Then provide:

Missing

Warm waterproof outerwear

Potential examples:

waterproof trench;
insulated jacket;
weatherproof parka.

Do NOT pretend the user owns these items.

F3. Unlock potential

If the existing wardrobe-analysis infrastructure can safely calculate this without changing recommendation logic, show:

Adding one suitable outer layer could unlock additional outfit combinations.

Only show a numerical count if the calculation is reliable.

Do not fabricate:

"8 outfits"

unless the system has actually calculated eight valid combinations.

F4. Product tone

The tone should feel like a stylist identifying a wardrobe gap:

Not:

❌ No outfits found.

Instead:

Your wardrobe is missing one piece for today's conditions.

That is a fundamentally better product experience.

F5. Future commerce readiness

Design the component so that a future version can support:

Shop this gap

but DO NOT implement commerce/product recommendations in Phase 5A.

The current release should simply identify the wardrobe capability gap.

TRACK G — FALLBACK PATH REGRESSION TEST

Phase 3.7 showed that the strict generator is robust, but the benchmark did not meaningfully exercise a genuine strict-generation failure.

Add one deterministic test.

The test must construct a case where:

strict generation genuinely produces no valid candidate;
relaxed generation has a legitimate candidate;
relaxed generation activates;
the resulting outfit remains valid;
no hard constraint is violated;
no garment is fabricated.

This is a test-only addition unless a genuine production defect is discovered.

Do not change fallback semantics merely to make the test pass.
