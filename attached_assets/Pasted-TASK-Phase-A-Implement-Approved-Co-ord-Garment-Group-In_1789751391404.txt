TASK: Phase A — Implement Approved Co-ord / Garment Group Infrastructure

Read `AMODKA-PROJECT-STATUS.md` first.

Also read the approved D.2 and D.2.1 specifications provided in the project/task context.

OBJECTIVE

Implement ONLY the approved Phase A garment-group infrastructure from D.2.1.

This is a persistence/security/domain-model implementation.

Do NOT implement multi-item classification, co-ord detection, UI, or styling behavior.

APPROVED ARCHITECTURE

Existing `WardrobeItem` remains the canonical identity of every independently wearable garment.

Add a separate relationship layer:

Source image/provenance
        ↓
GarmentGroup
        ↓
GarmentGroupMember
        ↓
existing WardrobeItem

Initial relationship types:

- `coordinated_set`
- `multi_item`
- `layered`

Initial confirmation statuses:

- `ai_inferred`
- `user_confirmed`
- `user_rejected`

A garment may belong to multiple distinct relationship groups.

The same garment must not appear twice in the same group.

Recommendation Engine v3.7 remains completely unchanged.

PHASE A IMPLEMENTATION SCOPE

1. DATABASE

Create:

`public.garment_groups`

Required fields:

- `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`
- `user_id uuid NOT NULL`
- `relationship_type text NOT NULL`
- `relationship_confidence double precision NULL`
- `confirmation_status text NOT NULL`
- `shared_attributes jsonb NOT NULL DEFAULT '{}'::jsonb`
- `source_image_path text NULL`
- `created_at timestamptz NOT NULL DEFAULT now()`
- `updated_at timestamptz NOT NULL DEFAULT now()`

Constraints:

- `user_id → public.user_profiles(id) ON DELETE CASCADE`
- relationship type limited to:
  `coordinated_set`, `multi_item`, `layered`
- confirmation status limited to:
  `ai_inferred`, `user_confirmed`, `user_rejected`
- confidence must be NULL or between 0 and 1
- `ai_inferred` requires non-null confidence
- `shared_attributes` must be a JSON object

Create:

`public.garment_group_members`

Required fields:

- `user_id uuid NOT NULL`
- `group_id uuid NOT NULL`
- `garment_id uuid NOT NULL`
- `created_at timestamptz NOT NULL DEFAULT now()`

Primary key:

`(group_id, garment_id)`

Composite foreign keys:

`(user_id, group_id) → garment_groups(user_id, id) ON DELETE CASCADE`

`(user_id, garment_id) → wardrobe_items(user_id, id) ON DELETE CASCADE`

If necessary, add:

`UNIQUE (user_id, id)`

to `wardrobe_items` so the composite foreign key is valid.

Do NOT add `set_id`, group columns, or relationship columns to `wardrobe_items`.

Do NOT rewrite existing wardrobe data.

3. INDEXES

Do not create speculative indexes.

4. RLS / SECURITY

Enable RLS on both new tables.

Authenticated users may only access rows where:

`auth.uid() = user_id`

Provide explicit SELECT/INSERT/UPDATE/DELETE policies.

Do NOT create broad `TO public FOR ALL` policies.

Anonymous users must have no table access.

Grant authenticated CRUD.

Grant service_role only the privileges required by the approved account-deletion flow:

- SELECT
- DELETE

Ownership must be enforced through the composite foreign keys as well as RLS.

Do not modify existing `wardrobe_items` RLS policies.

Do not clean up historical policy duplication as part of this task.

5. ATOMIC GROUP CREATION

Implement the approved transactional group-creation RPC.

Requirements:

- SECURITY INVOKER
- ownership derived/validated against `auth.uid()`
- do not trust arbitrary client-supplied user ownership
- group creation and initial membership insertion must be atomic
- minimum two distinct garment IDs
- duplicate garment IDs in initial input must fail
- every garment must belong to the authenticated user
- failure must leave neither the group nor memberships
- fully qualify database object names
- grant execution only as required
- revoke PUBLIC execution

Do not use separate client inserts with compensating cleanup.

9. LIFECYCLE

Deleting a wardrobe item must:

- remove its group memberships through FK cascade
- leave other wardrobe items untouched
- leave other group memberships intact

Deleting a group must:

- delete memberships
- NEVER delete wardrobe items

When the final group membership is removed, automatically delete the empty group.

Implement empty-group cleanup with a small SECURITY INVOKER trigger.

The trigger must be safe during parent-group cascade deletion.

A one-member group is allowed to exist after deletion of another member.
