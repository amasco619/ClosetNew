### Service-role account deletion — **SECURITY FAILURE**

**Test stopped here per spec.**

| Test | Actor | Operation | Expected | Actual | Result |
|---|---|---|---|---|---|
| E-affinity_signals | supabaseAdmin | `.delete().eq('user_id', userA_id)` no `.select()` | no error | **42501** | **FAIL** |
| E-wear_logs through E-saved_looks | — | — | — | Not reached | — |
| E-wardrobe_items | — | — | — | Not reached | — |
| E-user_profiles | — | — | — | Not reached | — |

**Exact error:**
```
code:    42501
message: permission denied for table affinity_signals
hint:    Grant the required privileges to the current role with:
         GRANT SELECT ON public.affinity_signals TO service_role;
details: null
```

**Root cause — PostgREST requires SELECT for all DELETE operations.**  
`postgrest-js` `delete()` without `.select()` sends a DELETE with no `Prefer: return=minimal` header. PostgREST defaults to `return=representation` for DELETE, executing `DELETE FROM table WHERE ... RETURNING *`. `RETURNING *` requires SELECT privilege in PostgreSQL. The migration `20260814000001_grant_service_role_min_privs.sql` grants only `DELETE` on the seven user tables — not `SELECT`. `user_profiles` has `SELECT, UPDATE, DELETE` so it would succeed; `wardrobe_items` has a prior corrective grant that includes SELECT.

**Production impact:** The account-deletion endpoints (`/api/user/delete-account` and `/api/user/delete-account-confirm`) loop over `affinity_signals`, `pair_affinity_signals`, `rotation_cursors`, `wear_logs`, `slot_statuses`, `tryon_profiles`, `saved_looks`. Each DELETE is `non-fatal` — the code logs a warning and continues. The auth user is still deleted, but rows in these seven tables remain in the database for deleted accounts indefinitely.

**Corrective action required (proposed as task #415):** Update `20260814000001_grant_service_role_min_privs.sql` to change the seven `GRANT DELETE ON` statements to `GRANT SELECT, DELETE ON`. No code changes needed — the existing delete pattern is correct.
