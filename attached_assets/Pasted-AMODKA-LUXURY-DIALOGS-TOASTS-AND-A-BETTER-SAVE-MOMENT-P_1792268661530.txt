AMODKA — LUXURY DIALOGS, TOASTS, AND A BETTER "SAVE" MOMENT

PROBLEM
The "Add this item? / Save this piece to your wardrobe now?" popup on the 
Add Item screen is a native system alert (blue uppercase Material buttons). 
It breaks the app's luxury feel, and it duplicates the "Save to Wardrobe" 
button the user just tapped. The app also uses native Alert.alert 
throughout (an older export had ~21 calls in add-item, bulk-review, 
outfits, profile, item-detail). Work from the live code; it may have 
changed.

STEP 0 — INVESTIGATE, REPORT BEFORE EDITING
a) Find the "Add this item?" dialog and explain WHY it exists (accidental 
   save protection? a guard for unreviewed/low-confidence attributes? 
   something else?). Check git history/comments if any.
b) List every Alert.alert / native confirm in the app with its purpose: 
   destructive confirm, permission message, rejected photo, 
   required-field validation, error.

STEP 1 — THE SAVE MOMENT (the main change)
- Single add: if Step 0a finds no real safeguard, REMOVE the confirmation. 
  Tapping "Save to Wardrobe" saves directly (guard against double-taps), 
  returns to the wardrobe, plays a light success haptic, and shows the 
  toast from Step 3: "Added to your wardrobe" with a small garment 
  thumbnail and Undo.
- If a real safeguard exists, keep a confirmation but use the new dialog 
  from Step 2 with copy like: title "Add to your wardrobe?", body "Your 
  piece will be saved with these details.", buttons "Save piece" and 
  "Keep editing". Prefer an inline prompt over a modal where possible, and 
  tell me what you chose and why.
- Bulk save ("Save N Items to Wardrobe"): same rule. Save directly, then 
  one toast "N pieces added" with Undo that removes the whole batch.
- Undo must delete the item(s) just added through the app's normal delete 
  path (database row, storage image, local guest copy, any caches), 
  and must not refund background-removal quota or break the item-cap 
  logic. Undo window about 5 seconds; after it, the toast just disappears.

STEP 2 — LuxuryDialog (replaces every native Alert)
Create components/LuxuryDialog.tsx plus a provider/hook, mounted in the 
root layout:
- API: `const dialog = useDialog()`; `await dialog.confirm({title, 
  message, confirmLabel, cancelLabel, tone: 'default' | 'destructive' | 
  'info', icon})` -> Promise<boolean>; `dialog.notify({title, message, 
  buttonLabel, icon})`. Also export a helper with the SAME signature as 
  Alert.alert(title, message, buttons) so migrating each call is 
  mechanical.
- Render with React Native's Modal (transparent, statusBarTranslucent), 
  NOT a plain overlay view in the root. The Add Item screen is 
  presented as a sheet, and an overlay in the root layout can render 
  underneath it on iOS.
- Backdrop: dimmed navy scrim (existing overlay/navyScrim tokens) with 
  expo-blur if already used elsewhere. Tap outside = cancel for 
  non-destructive dialogs only.
- Card: ivory surface from the existing palette (Colors.background / 
  white), 24px radius, generous padding, hairline champagne-gold border 
  (existing glassBorder / secondary tokens), soft shadow. Optional small 
  gold outline icon in a circular badge at the top.
- Typography: title in the app's heading typeface, body in the muted text 
  colour, no all-caps buttons, no system blue.
- Buttons STACKED, full width: primary = navy pill (Colors.primary, 
  light text); secondary = quiet text button in muted ink. Destructive 
  tone: muted rose/terracotta derived from Colors.error as text/outline 
  on the primary action, never a solid red block.
- Motion: backdrop fade plus card scale 0.96->1 with a short spring; 
  respect reduce-motion; light haptic on confirm.
- Behaviour: Android hardware back = cancel; accessibilityViewIsModal, 
  role alertdialog, announce the title; buttons at least 48dp; 
  works identically on iOS and Android.
- Copy voice: calm and warm, no exclamation marks. Rewrite stock copy, 
  e.g. "Remove Item / Remove this {subType}?" -> "Remove this piece?" / 
  "It will be taken out of your wardrobe." (check the real consequences, 
  e.g. saved looks, and state them accurately).

STEP 3 — Toast with action
Create a toast provider: glass pill (BlurView + existing glass tokens), 
bottom-anchored above the tab bar/safe area, entrance slide + fade, 
auto-dismiss (about 5s with an action, shorter without), optional 
thumbnail, optional action button ("Undo", "View") in champagne gold. 
Queue so two toasts never overlap. Accessible (announce message).

STEP 4 — MIGRATE EVERYTHING
Replace all Alert.alert usages with the new dialog or toast per Step 0b:
- Permission prompts: dialog.notify with an "Open Settings" action where 
  the current code offers one.
- Rejected photo: dialog.notify, gentle wording.
- Remove item: dialog.confirm, tone 'destructive'.
- Errors: dialog.notify, or a toast if non-blocking.
Leave genuinely native system prompts (OS permission dialogs) alone.

STEP 5 — OPTIONAL, ONLY IF SAFE (do last; skip and tell me if risky)
The "Type required / Color required / Fit required / ..." popups on Add 
Item are blocking dialogs for form validation. Replace them with inline 
validation: scroll to the first missing field, highlight it with a 
subtle gold/rose outline and a one-line hint beneath it, and show no 
modal. Keep the validation rules themselves unchanged.

CONSTRAINTS
- No new heavy dependencies; reuse existing tokens/fonts/components.
- Don't change save logic, quotas, classification, or auth, except 
  adding the Undo path.
- Keep accessibility labels and screen-reader behaviour.
