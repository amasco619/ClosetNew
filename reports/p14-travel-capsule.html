Corrective patch — outage preservation and stale wardrobe retries

Both review findings are corrected at the planner boundary. No AppContext, view, helper, styling service or Outfits integration changes were needed.

  • The last authorized active-wardrobe/public-catalogue revision is retained through verification outages. The full canonical wardrobe revision remains live, so real wardrobe edits still invalidate assignments. Temporary Free/Premium projection changes alone no longer erase the draft.
  • During unavailable verification, protected choices, assigned looks, checklist and essentials remain hidden and noninteractive. Recovery waits for React to commit the authorized Premium projection, then reconciles every assigned look with current owned IDs, public candidates and authoritative group membership. Assigned Traditional looks use the existing dedicated service, including its notice/provenance, even when another slot is selected. Missing/invalid choices are discarded before review reopens.
  • Confirmed loss still resets the whole draft. Automatic recovery cannot supersede that revocation. Account changes and genuine underlying wardrobe/catalogue changes still invalidate the draft as before.
  • Wardrobe retry callbacks capture owner, request version and revision, and require the planner to remain mounted. Both stale success and failure are ignored. A late account-A read cannot replace account B's verified state or initiate another verification for B.

3. Exact behavior implemented

  • Open Plan a travel capsule in Outfits. Sign-in is required. Successful authoritative Premium verification enables the temporary planner only after startup and full wardrobe pagination are complete.
  • Choose 1–7 ordinal days. Add/remove up to 28 activity slots. The initial slot is Day 1 / Casual. No destination, calendar dates, travel history or new profile preference is collected.
  • Supported exact mappings: Casual→casual, Work→work, Dressy date→date-dressy, Event→event, Wedding→wedding, Travel→travel, Resort→resort, Active→active, Traditional→traditional-event. Other/unsupported has no scenario and stays unfilled.
  • Generic selection uses only exact matches from useApp().outfitSets. Traditional calls getStylingRecommendations('traditional'), not a generic fallback. Its notice and original relationship-bearing outfit object survive assignment and review.
  • Every component must be owned === true with a nonblank ID in the current active wardrobe. Invalid or unavailable looks are rejected rather than repaired or partially packed.
  • Stable look keys combine exact scenario and sorted unique owned component IDs. Daily result IDs and array positions are not identity. Selecting an already assigned look for another slot uses an explicitly labelled Reuse this look action.
  • Coverage is assigned/total activity slots, including unsupported and empty slots in the denominator. It is not a statement that every trip day is planned. Removing an activity removes it from the denominator.
  • The owned checklist uses current wardrobe objects and deduplicates by actual item ID. Documents, chargers and toiletries are separate optional essentials, never invented wardrobe garments.
  • Canonical wardrobe/catalogue/profile/weather changes invalidate assignments. Account changes and confirmed entitlement loss reset the entire draft. Closing, tab blur, unmount or ending the session discards it.

4. Relationships, access and failure handling

getGarmentGroups(owner) supplies authoritative Phase A records, passed through the existing owner/member validation projection. Generic full-set participation is disclosed as membership, not construction provenance. Partial participation explicitly states used/total pieces. No matching-colour/name/photo inference and no new generic all-or-none rule. Dedicated Traditional outputs with partial confirmed sets or obsolete supplied provenance are rejected.

Entry/slot retrieval and every accepted choice perform strict refreshPremiumEntitlement(true). A confirmed false is a non-entitlement state and resets protected draft data; failed verification is an unavailable/retry state. Group-read failure is a retryable failure, not an empty group list. Traditional reads reconcile group membership before/after service completion.

Request revisions and current identity/input snapshots reject superseded results. A read-only 30-second group poll detects external membership changes without requesting more styling results or polling Premium; foreground rechecks access/groups. Membership changes clear assignments. Read failure pauses protected review. This is bounded polling, not instant realtime.

Planner actions invoke no profile, mood, reaction, wear, saved-look, rotation or persistence mutation APIs. Existing AppContext hydration and entitlement-related effects retain their normal lifecycle; this report does not claim a running app performs zero background writes. The planning draft, checklist ticks and essentials exist only in component memory.

8. Limitations and unverified behavior

  • The finite currently selected catalogue can supply zero looks for a supported activity; no backfill, reseeding or hidden-pool workaround. Four days may require explicit reuse or remain partly unfilled.
  • No destination forecasts, calendar-specific styling, optimisation or full-coverage guarantee. Current selected outfits may already reflect the existing current-weather pipeline.
  • The draft is deliberately not saved or resumable. Dismissal, navigation and session loss discard it; input changes can clear choices. This limitation is displayed in the planner.
  • External group changes are detected on the polling/foreground/acceptance freshness paths, not instantaneously.
  • Mounted native-host tests use controlled context and group boundaries, not real authentication, real subscription billing, live Supabase data or an instrumented real-AppContext network/persistence trace.
  • The new signed-in planner has not been interactively browser-tested or tested on an iOS/Android device. Native layout, VoiceOver/TalkBack and actual browser accessibility announcements remain unverified. Native/ARIA control semantics are present and mounted tests cover checked state, but do not establish actual screen-reader behavior.
  • The entire 90-suite project suite was not run for this bounded change. The existing billing-contract failure remains outside scope; no full-project-green claim.

Final status: requested bounded functionality implemented; focused checks and golden regression pass. No protected-area expansion or deployment.
