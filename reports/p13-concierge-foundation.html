3. Actual journey and styling handoff

  1. Open Outfits and tap Plan an occasion. The guided modal stays on the existing route; the four-tab navigation is unchanged.
  2. Guests see the existing sign-in path. Signed-in users receive a fresh authoritative Premium refresh before the choices are enabled. Confirmed non-Premium users can open the existing Premium screen; failed verification offers retry instead.
  3. Select one supported radio option. Submit stays disabled until there is a valid choice. Details explain today-only scope and the limited Traditional context.
  4. Submission performs a second fresh verification and runtime intent validation. Only a current successful request can commit a transient plan and scenario.
  5. Generic choices display outfitSets.filter(o => o.scenario === selectedScenario). Traditional clears old output and starts the existing dedicated request. This is a real handoff, not a new title over stale cards.
  6. The existing result cards display owned pieces, explanations, wear actions, reactions and sharing. A readiness summary is in the existing vertical results scroll.
  7. Retry retrieval failures, change the occasion, or exit. Closing/exiting, manual scenario changes, account changes and tab blur discard the transient intent. No plan is saved.

Same-occasion Traditional submission increments its request revision and rereads relationships. Generic resubmission continues using the current reactive AppContext scenario output; it does not regenerate a competing pool, reset quotas or advance a separate rotation.

4. Traditional styling and confirmed relationships

The existing AppContext service remains responsible for owner-checked garment-group retrieval, account/startup continuity, canonical wardrobe projection, typed relationship projection, Traditional candidate construction and the existing daily selector. None of those styling modules were edited.

The browser fixture deliberately included six earlier decoy bottoms. Explicit Traditional still returned the actual BUBA + IRO coordinated unit, owned heels/bag and Styled as a set. Reselecting the same brief caused another groups GET. Returning a failed groups read produced failure, not an empty relationship list.

Unknown semantics, persisted user corrections and raw confirmed relationships remain intact. Generic outputs are not advertised as universally relationship-aware. Layered/multi-item membership is not promoted into new construction rules. Traditional intent does not establish ceremony role, cultural identity, matching requirements or mandatory headwear.

5. Access, readiness and stale-response behavior

Authentication and entitlement

Entry and submission reuse the existing authoritative entitlement refresh. Its opt-in strict mode distinguishes a confirmed false from failed/missing-session/superseded verification; default callers remain backward-compatible. The results boundary also checks current signed-in identity, plan ownership, Premium state and absence of an unavailable-entitlement flag. There are no route parameters to trust.

Unavailable access pauses the planner with retry and no upgrade claim. Confirmed non-entitlement uses the existing Premium screen. No client cache, claims or planner selection grants Premium. Revocation between entry and submit was verified to block the handoff.

Distinct outcomes

StateCondition and response
LoadingWardrobe/pagination/startup or Traditional styling still pending. No insufficiency or weather-readiness conclusion.
ReadyKnown complete wardrobe and completed styling with actual returned results.
Insufficient wardrobeSuccessful complete load with an empty active wardrobe. Guidance is to add owned clothing—not an invented culturally mandatory piece.
Empty resultKnown nonempty wardrobe and successful relevant styling outcome without a viable look. Review owned pieces or choose another occasion.
FailureWardrobe/startup/relationship/styling retrieval failed. Explicitly not presented as a wardrobe gap; existing initialization/load/Traditional retry paths are reused.
Access unavailableFresh Premium verification failed or was superseded. Selection pauses with retry.
Not entitledFresh current verification successfully confirmed non-Premium. Existing Premium CTA, not an outage message.

Transient request versions and current-owner checks reject late access results; existing active-effect guards and AppContext account continuity reject late Traditional results. Old cards are cleared on repeated Traditional submission and suppressed during Concierge loading/failure. Account/blur/exit cleanup prevents a plan from carrying into another session.

Selection does not update profile preferences, daily mood, wear history or saved looks. Existing actions only run when explicitly pressed. Existing weather is displayed only when its underlying state is known: global Celsius default and explicit Fahrenheit are preserved, switched-off weather is stated, and absent weather is not described as warm or dry.

  • No unresolved blocker within the approved P1.3 scope.
  • Live billing, real authentication/cloud data, store purchase/restore, production readiness, native-device behavior and VoiceOver/TalkBack were not verified. Browser access/data came from controlled synthetic HTTP responses.
